# T1-S02 — 1H core service: Verified Reset Service

Repo: td-1-helpdesk · Environment: td-1-helpdesk (Keycloak 26.8.1 at http://localhost:8080) · Day: D1 · Time box: 120 minutes · Credit cap: $12

## Goal
Build the core of 1H: a small FastAPI web service that a helpdesk agent uses to run a password or MFA reset, where the verification steps cannot be skipped or reordered — callback to the phone number on file, one-time code from the registered device, manager approval for privileged accounts, a temporary password that dies after 60 minutes, and an alert on any MFA change within 24 hours of a reset. Keycloak (an open-source identity server) plays the company's login system. This session delivers the service, unit tests that run with Keycloak faked, and a script that builds the dev realm. Replay tests, the final audit-log work, the README diagram and the demo come in T1-S03.

## Steps
1. Director (Plan mode): read this brief, take the two design decisions below (D1, D2), propose the plan, wait for approval. Record both decisions in the plan and later in the 1H README "Limits".
   - **D1 — how the service checks a one-time code against Keycloak.** Keycloak does not expose an admin API that says "is this TOTP code valid for user X". Options: (1, stretch only if AC1–AC6 already pass and time remains) a dedicated confidential client `reset-verifier` whose direct-grant flow is a copy of the built-in one with the Password step disabled, so the token endpoint accepts `grant_type=password` + `username` + `totp` and answers 200 (valid) or 401 (invalid); the override is bound to that one client only, so normal logins still need the password. `TODO(verify): Keycloak 26 admin REST — disabling the password execution in a copied direct-grant flow and binding it through the client's authenticationFlowBindingOverrides.` (2, DEFAULT — chosen by the director on Oct 21 to protect the $12 cap) the service keeps a dev copy of each user's TOTP seed in a gitignored file written by `keycloak-dev.sh` and verifies with `pyotp`; the README must then say plainly that a real deployment would never hold the seed outside the identity provider.
   - **D2 — how the service checks the manager's token on approval.** Options: (a, preferred, no new dependency) Keycloak token introspection (`POST /realms/maple-harbour/protocol/openid-connect/token/introspect`) using a confidential client `reset-service` whose secret `keycloak-dev.sh` generates and writes to `1h-verified-reset/.dev/reset-service.secret` (gitignored like the seeds, never committed or printed), where the service, the tests and `demo.sh` read it; (b) verify the JWT signature against the realm's JWKS with `pyjwt[crypto]==2.15.1` (version checked on PyPI 2026-10-21; add it to `requirements.txt` only if chosen).
2. `builder`: start Keycloak and confirm it answers (not in CI; in the session only):
   `nohup env KC_BOOTSTRAP_ADMIN_USERNAME=admin KC_BOOTSTRAP_ADMIN_PASSWORD=dev-only-not-secret /opt/keycloak/bin/kc.sh start-dev --http-port=8080 > /tmp/keycloak.log 2>&1 &` (its log is `/tmp/keycloak.log`), then poll in separate short commands of at most 100 seconds each, `curl -s -o /dev/null -w '%{http_code}' http://localhost:8080/realms/master` until it prints 200 (first start takes about 45 seconds). The dev password is a documented throwaway for a local test server, never reused. If `/opt/keycloak` is missing, see Known caveats.
3. `builder`: `scripts/keycloak-dev.sh` — idempotent (safe to run twice): starts Keycloak with the command above if port 8080 is not answering and waits for `/realms/master`; gets an admin token from the master realm (`admin-cli` client, password grant, password from `KC_BOOTSTRAP_ADMIN_PASSWORD`, default the throwaway above); creates realm `maple-harbour` if absent; realm role `manager`; group `privileged`; the clients from D1/D2; and four users taken from the 1E tickets' staff list, each with a `phone` attribute in `555-01xx` form and an email at `mapleharbour.example`: one regular user with a TOTP device, one `privileged` group member with a TOTP device, one manager (role `manager`, a dev password), and one regular user with **no** TOTP device. TOTP seeds are generated at run time and written only to `1h-verified-reset/.dev/seeds.json` (add `.dev/` to `.gitignore`), which tests read; nothing secret is printed to the session or committed. With option 2 (the default) skip seeding OTP credentials into Keycloak entirely: the registered-device list is `.dev/seeds.json`. (Only for the option-1 stretch: `TODO(verify): the Keycloak 26 credential representation for seeding an OTP credential through the admin API, or a partial realm import.`)
4. `builder`: the service in `1h-verified-reset/app/` (`main.py`, `models.py`, `state.py`, `keycloak.py`, `audit.py`, `clock.py`), run with `uvicorn app.main:app --port 8000` from `1h-verified-reset/` (8080 belongs to Keycloak). Configuration by environment variables with documented defaults (`KEYCLOAK_URL`, `KEYCLOAK_REALM=maple-harbour`, `AUDIT_LOG_PATH`). Requests live in memory (a lab, not a product — say so in the README). Endpoints and rules:
   - `POST /reset-requests` body `{kind, claimed_username, agent_id, channel}` with `kind` one of `password`, `mfa_reset`, `mfa_enrol_device`, `mfa_change_phone` — every identity-related request goes through the same chain (AL26-010: "out-of-band verification procedures for identity-related requests"). Looks the user up in Keycloak; unknown user → state `BLOCKED` (reason `unknown_user`). Otherwise `OPEN`, and the response shows the phone number on file (the callback is simulated: the agent dials it and records what happened).
   - `POST /reset-requests/{id}/callback` body `{number_dialed, reached}` — a number other than the one on file always → `BLOCKED` (`callback_wrong_number`); not reached → `BLOCKED` (`callback_not_reached`); reached → `CALLBACK_DONE`.
   - `POST /reset-requests/{id}/otp` body `{code}` — user with no registered OTP device → `ESCALATED` (`no_registered_device`); wrong code three times → `BLOCKED` (`otp_failed`); valid (per D1) → `OTP_VERIFIED`, then `AWAITING_APPROVAL` if the user is in group `privileged`, else `APPROVED`.
   - `POST /reset-requests/{id}/approve` with `Authorization: Bearer <Keycloak token>` — token must be valid (per D2) and carry realm role `manager`; the approver must not be the claimed user; otherwise 403 and an audit line. Success → `APPROVED`.
   - `POST /reset-requests/{id}/issue` — only from `APPROVED`. `password`: set a random temporary password in Keycloak (`temporary: true`), return it **once** with `expires_at` = now + 60 minutes; the audit line records that a password was issued, never the value. `mfa_reset`: remove the user's OTP credential; `mfa_enrol_device`: add Keycloak's configure-TOTP required action; `mfa_change_phone`: update the `phone` attribute. Then `COMPLETED`.
   - Rule 5 (24-hour watch): an MFA-kind request created within 24 hours after a `COMPLETED` password reset for the same user writes an alert to `alerts.jsonl` (recommended, director's call: also force `AWAITING_APPROVAL` regardless of group — justify in the README). `POST /mfa-change-events` body `{username, change, source}` records an MFA change observed outside the service (in the lab, tests and the demo send it) and alerts on the same 24-hour rule. `GET /alerts` lists alerts.
   - Any step called out of order → HTTP 409 and an audit line `out_of_order`. `GET /reset-requests/{id}` returns state and history with no secrets.
   - `POST /maintenance/expire-temp-passwords` rotates any temporary password older than 60 minutes to a new random value nobody is told (Keycloak's "temporary" flag only forces a change at next login; it does not time-limit the password — the service does).
   - `audit.record(event)` appends one JSON object per line to `audit.jsonl` (`ts, request_id, actor, action, outcome, details`) — the final append-only checks and tests come in T1-S03. Time comes from `clock.now()` so tests can move it.
5. `builder`: tests first where practical. `tests/unit/` with a `FakeKeycloak` (same interface as `keycloak.py`), covering at least: happy path for a regular user; callback to a different number → BLOCKED; three wrong codes → BLOCKED; OTP before callback → 409 with audit line; privileged user → AWAITING_APPROVAL, `issue` → 409, non-manager token → 403, self-approval → 403, manager → APPROVED; user without OTP device → ESCALATED; unknown user → BLOCKED; the temporary password never appears in the audit log; MFA-kind request 23 h after a reset → alert, 25 h → none; MFA change event inside and outside 24 h; expiry rotation after 60 minutes; every audit line is valid JSON with the required fields. `tests/integration/` marked `@pytest.mark.keycloak`: realm exists, `keycloak-dev.sh` run twice leaves the same users, happy path against the real server with `pyotp` generating the code from `.dev/seeds.json`. `tests/conftest.py` skips the marker when `GET http://localhost:8080/realms/maple-harbour` is not 200. Add a root `pyproject.toml` registering the `keycloak` marker, setting `[tool.pytest.ini_options] pythonpath = ["1h-verified-reset"]` (the folder name starts with a digit and has hyphens, so it cannot be a Python package; `app` must be importable from it), and setting ruff's target to Python 3.12.
6. `builder`: a draft `1h-verified-reset/README.md` — what it does (plain), how to run (Keycloak start, dev script, uvicorn, tests), the state machine as a list, D1/D2 decisions, Limits so far. T1-S03 finishes it.
7. `verifier`: check the acceptance criteria; write `docs/verify/T1-S02.md`; run the integration tests only if Keycloak is up and say which ran.
8. `wrap`: update `docs/RUN-SHEET.md` (T1-S02 → DONE), `COSTS.md`, `AI-USE.md` (1H section), `docs/CAVEATS.md`; push branch `t1-s02-reset-core`; print the PR title and body.

## Known caveats
- `TODO(verify)`: D1 option 1 (direct-grant flow without the password step) and the admin-API representation for seeding OTP credentials — both against the Keycloak 26 documentation.
- Keycloak's temporary password forces a change at next login but has no time limit; the 60-minute expiry is enforced by the service and must be described that way in the README.
- First Keycloak start takes about 45 seconds; `start-dev` is for a lab only. The dev data lives inside the session's disk and may be gone next session — re-run `keycloak-dev.sh` at the start of every session that needs it.
- If `/opt/keycloak` is missing (environment setup printed `WARN`), run `bash environment/setup.sh` inside the session; if `/opt` is not writable, extract to `$HOME/keycloak` and make the scripts honour `KC_HOME` (default `/opt/keycloak`); record a caveat.
- Port 8080 is Keycloak's; the service runs on 8000. Keep it that way in every script and test.
- A generated TOTP seed looks like a secret to gitleaks — `.dev/` must stay gitignored, and the seeds must never be printed into the chat.
- The environment bootstrap variables are Keycloak 26's `KC_BOOTSTRAP_ADMIN_USERNAME` / `KC_BOOTSTRAP_ADMIN_PASSWORD` (from the spec); older `KEYCLOAK_ADMIN` names are not used.
