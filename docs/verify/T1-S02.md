### Extra review of the whole diff (my own findings)

**F1 — should fix (cheap; best done in T1-S03): Rule 5 can be dodged by order.** Rule 5 is checked only when an MFA request is **created**. If an MFA request is opened *before* the password reset completes, then carried on after it, the request raises no alert and needs no manager. I showed this with a throwaway script (no repo change) using the unit-test fake:
`(a) MFA request opened before reset -> state after code: APPROVED | alerts: 0` and then `issue -> COMPLETED`.
This matches the brief's exact words ("created within 24 hours after…"), so it is not an AC failure. But it is the exact "password, then MFA" takeover sequence that Rule 5 exists for, and a T1-C1 interviewer could find it. Suggested fix: run the rule-5 check again at the `otp` step (before choosing `APPROVED` or `AWAITING_APPROVAL`) and at `issue`.

**F2 — low (fails safe): an older temp-password record can rotate a newer temp password early.** Two password resets for the same user 50 minutes apart: at minute 60 the maintenance job rotates the user's *current* password (the second one, 10 minutes old), because it only checks that `UPDATE_PASSWORD` is still pending. Evidence: `(b) second temp password age 10 min; rotations at t+60: 1 | second password still current in Keycloak: False`. The result is a shorter life, never a longer one. Fix: skip a record when a newer temp password for the same user exists.

**F3 — low: approver and agent are never compared.** `agent_id` is free text, and only "approver ≠ claimed user" is enforced, which is what the brief asks. A manager could act as the agent and also approve. README Limits already says no endpoint authenticates the agent. Worth one line there.

**F4 — low: odd response shapes from Keycloak still give a 500.** `raw["id"]`, `g["name"]` and `cred["id"]` raise `KeyError`, which `keycloak_call` does not catch. Network and JSON errors are handled correctly.

**F5 — note: Keycloak calls run while the global store lock is held.** With a 10 s httpx timeout, one slow call stalls every request. The code says this on purpose ("simple and slow is fine for a lab"), so it is acceptable here.

**Nits.**
- N1: the integration tests hard-code `localhost:8080` (`TOKEN_URL`, `test_realm_exists`), but the skip check honours `KEYCLOAK_URL`.
- N2: the integration tests change the real dev realm: `priya.nair` and `daniel.okafor` get temporary passwords. This is harmless in the lab.
- N3: when the user is gone, the expiry job logs `reason="already_changed"`. The label is wrong for that case.
- N4: `keycloak-dev.sh` writes `.profile.json` directly in `.dev/`, not in `$WORK`, so it is left behind if the PUT fails. It is gitignored and not a secret.
- N5: pytest warns `StarletteDeprecationWarning: Using httpx with starlette.testclient is deprecated`. It is harmless at today's pins, but watch for it when fastapi is bumped.

**Unsafe patterns and secrets:** none found. The temporary password is returned once and never stored or logged. Error labels carry only status and path. The script sends secrets through files, never through argv. `.dev/` is created with `chmod 700` under `umask 077`.

**Code Eojin may struggle to explain (prepare for T1-C1):** in `keycloak-dev.sh`, why `api()` sends `kill -TERM $$` (an `exit` inside `$( )` would leave only the subshell) and why the admin token is cached in a file; why `valid_window=1` is used; how the 8-thread test proves the lock works; why the audience mapper on `helpdesk-console` is needed.
